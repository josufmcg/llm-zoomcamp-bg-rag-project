# Baldur's Gate RAG Project — Complete Plan

## Overview

A Retrieval-Augmented Generation (RAG) system that answers questions about **Baldur's Gate II: Shadows of Amn** character creation classes. The system retrieves relevant information from a PostgreSQL knowledge base (using vector, keyword, and hybrid search) and generates answers using OpenAI's `gpt-4.1-mini`.

**Domain:** Baldur's Gate II character creation — 11 base classes (Fighter, Ranger, Paladin, Barbarian, Cleric, Druid, Monk, Thief, Bard, Mage, Sorcerer), their kits/subclasses, abilities, restrictions, and gameplay recommendations.

**Source material:** [GameFAQs BG2:EE Character FAQ by DHansen](https://gamefaqs.gamespot.com/pc/663934-baldurs-gate-ii-enhanced-edition/faqs/14105)

```
                                    │ OpenAI API                         │

                              │  OpenAI  │                        │   port 3000   │
                              └──────────┘                        └──────────────┘
```

- **FastAPI** (backend): Exposes REST endpoints for document ingestion, search, RAG question-answering, and feedback. Owns all business logic.
- **Streamlit** (frontend): Thin UI client that calls FastAPI via HTTP. Displays conversations, metrics, and collects user feedback.
- **PostgreSQL + pgvector** (storage): Single database for everything — document storage with vector embeddings, conversations, and feedback. Supports vector similarity search and full-text keyword search.
- **Grafana** (monitoring): Auto-provisioned dashboard reading from PostgreSQL. Displays conversation metrics, cost tracking, relevance distribution, and user feedback.

## Components

### 1. Dataset (data/bg_characters.json)

LLM-assisted extraction of character class information from the GameFAQs BG2 Character FAQ. Each record represents one of the 11 base character classes.

**Schema:**
```json
{
  "id": "fighter",
  "category": "Character Creation",
  "subcategory": "Fighter",
  "question": "What is the Fighter class and how should I play it?",
  "text": "The fighter is a champion, swordsman, soldier, and brawler... [full class description including kits, abilities, restrictions, and recommendations]"
}
```

**Records (11 total):** Fighter, Ranger, Paladin, Barbarian, Cleric, Druid, Monk, Thief, Bard, Mage, Sorcerer.

Each record's `text` field includes: class description, special abilities, restrictions, general gameplay comments, and all kit/subclass variants with their own abilities, restrictions, and comments.

The `question` field is a natural-language question that the text answers (e.g., "What is the Fighter class and how should I play it?").

An `id` field provides a unique, human-readable identifier (lowercase class name).

A `doc_hash` (MD5 of `category + subcategory + question + text`) is computed at ingestion time for deduplication — **not** stored in the JSON file.

### 2. Backend — FastAPI Service

REST API service handling all business logic. Runs on port 8000.

**Endpoints:**

| Method | Path | Description | Request Body | Response |
|--------|------|-------------|-------------|----------|
| `POST` | `/documents` | Ingest one or more documents | `{documents: [{category, subcategory, question, text}]}` | `{ingested: N, skipped: N}` |
| `GET` | `/search` | Search knowledge base | Query params: `q`, `method` (vector/keyword/hybrid), `limit` | `{results: [{id, category, subcategory, question, text, score}]}` |
| `POST` | `/ask` | RAG question answering | `{question: str, search_method: str}` | `{answer, question, model, search_method, prompt_tokens, completion_tokens, total_tokens, response_time, cost, conversation_id}` |
| `POST` | `/feedback` | Submit user feedback | `{conversation_id: int, score: int}` | `{status: "ok"}` |
| `GET` | `/health` | Health check | — | `{status: "healthy"}` |

**Key implementation details:**
- FastAPI lifespan event initializes DB connection pool, loads embedder model, and creates RAG pipeline instance.
- Dependencies are injected via FastAPI's `Depends()` mechanism.
- The `/documents` endpoint computes embeddings and MD5 hashes, then upserts (skip if hash exists).
- The `/ask` endpoint runs the full RAG pipeline: search → build context → build prompt → call OpenAI → save conversation to DB → return answer with metrics.
- The `/ask` endpoint also triggers an async LLM-as-judge evaluation that saves relevance feedback to the feedback table.

### 3. Search Engine (src/bg_rag/search.py)

Three search methods, all querying PostgreSQL:

- **Vector search:** Compute query embedding with the ONNX model, find nearest neighbors using pgvector's cosine distance operator (`<=>`). Returns documents ordered by cosine similarity.
- **Keyword search:** Use PostgreSQL's built-in full-text search (`to_tsvector` / `to_tsquery` / `ts_rank`). The `text`, `question`, and `subcategory` fields are indexed with configurable weight boosts (e.g., subcategory:A, question:B, text:C).
- **Hybrid search:** Run both vector and keyword searches, then combine results using **Reciprocal Rank Fusion (RRF)**: `score = Σ 1/(k + rank_i)` with `k=60`. This balances semantic similarity with keyword relevance.

All methods accept a `limit` parameter (default: 5) and return results with a normalized score.

### 4. RAG Pipeline (src/bg_rag/rag.py)

Adapted from the reference project's `RAGBase` pattern:

1. **Search:** Call `search.hybrid_search(query)` (default) or specified method.
2. **Build context:** Format search results into a text block with category, subcategory, question, and text fields.
3. **Build prompt:** Insert context into prompt template with the user's question.
4. **LLM call:** Send system instructions + user prompt to OpenAI `gpt-4.1-mini` via the Responses API (`client.responses.create()`).
5. **Track metrics:** Record prompt_tokens, completion_tokens, total_tokens, response_time, cost in an `LLMCallRecord` dataclass.

**System instructions** are tailored for the BG2 domain (not generic "course assistant" instructions from the reference).

**Cost calculation:** Based on `gpt-4.1-mini` pricing (input: $0.40/M tokens, output: $1.60/M tokens).

### 5. Evaluation System (scripts/)

Two-phase evaluation following the reference project's pattern:

**Phase 1 — Ground truth generation** (`scripts/generate_ground_truth.py`):
- For each of the 11 documents, use OpenAI to generate 5 natural-language questions that the document answers.
- Store as `data/ground_truth.csv` with columns: `doc_id, question, doc_category, doc_subcategory`.
- Total: ~55 ground truth question-document pairs.

**Phase 2 — Search evaluation** (`scripts/evaluate.py`):
- For each ground truth question, run all three search methods.
- Compute **Hit Rate@5** (did the correct document appear in top 5?) and **MRR@5** (reciprocal rank of the correct document).
- Support boost parameter tuning: vary field weights for keyword search and compare metrics.
- Output results as a table and save to CSV.

**Phase 3 — Answer evaluation** (runtime, via `src/bg_rag/judge.py`):
- LLM-as-judge: After each RAG answer, use OpenAI structured output to classify relevance as `RELEVANT`, `PARTLY_RELEVANT`, or `NON_RELEVANT`.
- Uses Pydantic model for structured parsing with retry logic.
- Results saved to the `feedback` table with `source='judge'`.

### 6. Frontend — Streamlit Application

**Main app** (`src/bg_rag/frontend/app.py`):
- Text input for user questions.
- "Ask" button triggers `POST /ask` to FastAPI.
- Displays: answer text, response time, token counts, cost.
- Thumbs up/down buttons send `POST /feedback` to FastAPI.
- Conversation history panel showing recent Q&A pairs.

**Dashboard** (`src/bg_rag/frontend/dashboard.py`):
- Summary metrics: total conversations, avg response time, total cost, avg tokens.
- Charts: cost over time, response time over time.
- Judge relevance distribution (bar chart).
- User feedback summary (thumbs up vs down counts).

### 7. Monitoring — Grafana Dashboard

Auto-provisioned via docker-compose volume mounts:

- **Datasource:** PostgreSQL (same database as the application).
- **Dashboard panels:**
  - Conversations over time (time series).
  - Average response time (gauge + time series).
  - Total cost and cost per conversation (stat + time series).
  - Token usage distribution (bar chart).
  - Judge relevance breakdown (pie chart).
  - User feedback ratio (stat panels).
  - Recent conversations table.
